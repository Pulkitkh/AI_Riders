# PRAHARI — System Workflow

**SIH 2026 · PS ID SIH26145 · NTRO · Team AI Riders**
AI-Based Detection of Cyber Threats in Unidirectional (read-only) IP Traffic.

PRAHARI observes a *copy* of production-side traffic through a one-way boundary and
raises ranked, explainable threat alerts without ever being able to transmit back
into the protected network. This document traces one packet from the wire to a
ledgered alert.

---

## 1. Ingest (read-only)

A passive optical/SPAN tap or a data-diode feed delivers packets (or NetFlow v5)
to the sensor host. PRAHARI's detection engine opens **no** sockets toward the
source, performs no enrichment lookups, and has no transmit path. This is a
software invariant asserted by `prahari/selftest.py` (an AST/import scan) and is
one of *three* layers of the one-way argument — see `docs/SECURITY.md` for the
physical-diode and OS/network layers.

Supported ingest today: offline PCAP replay, live `AF_PACKET` capture on Linux,
and NetFlow v5. IPv6/IPFIX/NetFlow-v9 are scoped as next steps (see the coverage
table in the README).

## 2. Flow assembly (`prahari/pcapread.py`, `prahari/netflow.py`)

Packets are grouped into bidirectional flow records (`prahari.schema.Flow`):
5-tuple, byte/packet counts each way, TCP flag counts, the signed packet-size
sequence, and passively-read application metadata — DNS qname/qtype, TLS
JA3/JA4/SNI/cert facts, and OT/ICS header fields (Modbus/DNP3/IEC-104 function
and unit). **No payload is decrypted.** Every flow carries a stable `flow_id`.

## 3. Streaming detection (`prahari/engine.py`, `prahari/detectors/`)

The engine advances a window clock as flows arrive and evaluates every detector
at each window boundary, emitting alerts immediately (incremental, not
end-of-run). Detectors:

| Detector | Method | Class |
|---|---|---|
| DDoS | entropy / rate / CUSUM / reflection heuristics | `volumetric_ddos` |
| C2 beaconing | logistic regression over periodicity/jitter/shape | `c2_beaconing` |
| DGA | lexical / n-gram / dictionary-word features | `dga_resolution` |
| DNS tunnelling | query length / type / uniqueness | `dns_tunnelling` |
| Encrypted (TLS) | JA4/JA3 rarity + cert + packet-shape | `encrypted_malware` |
| Recon | fan-out + unanswered-ratio (degrades one-way) | `recon_scanning` |
| Exfiltration | logistic regression over volume/asymmetry/locality | `data_exfiltration` |
| OT/ICS | Modbus/DNP3/IEC-104 header + learned-poller policy | `ics_intrusion` |
| Anomaly | Isolation Forest over benign vectors (corroborating) | `anomalous_traffic` |

Three detectors (beacon, DGA, exfil) use a fitted logistic model; the anomaly net
is an unsupervised Isolation Forest positioned as a corroborating net for
**previously unseen behaviour**, not a proven zero-day oracle.

## 4. Fusion & calibration (`prahari/fusion.py`, `prahari/model.py`)

Raw detections are **deduplicated** (a flood is one event), **correlated** into
per-entity incidents (a kill chain, not three alerts), and **calibrated**: each
detector's raw score is mapped through a fitted isotonic calibration table so a
reported confidence of 0.9 means roughly nine-in-ten empirically. The alert keeps
both the raw `score` and the calibrated `confidence`; calibration quality
(ECE/Brier) is reported by `eval/report.py`. Every alert is stamped with its
MITRE ATT&CK (and ATT&CK-for-ICS) technique.

## 5. Evidence & audit (`prahari/ledger.py`)

Each alert is appended to a SHA-256 **hash-chained, tamper-evident** ledger (not
a regulatory-certified immutable store — external WORM/anchoring is future work).
The alert schema (ECS-shaped) carries timestamp, non-empty flow id(s), threat
class, calibrated confidence, evidence, and the MITRE technique.

## 6. Presentation (`web/`, `sensor/`)

A read-only dashboard renders ranked incidents with a plain-language explanation
of every alert. The **live sensor** and **demo attack injector** are deliberately
*outside* the `prahari/` detection package (they own sockets) and are gated to a
demo profile — never enabled in a hardened deployment.

## One canonical evaluation

Every performance number in the deck, README, and web viewer is generated by a
single command:

```
python3 eval/report.py      # writes eval/report.json — the one source of truth
```

It reports strict per-class precision/recall/F1, a separate host-detection F1, a
strict confusion matrix, false-positive events vs hosts vs rate, detection-window
delay percentiles, and dataset composition — all on held-out captures whose seeds
and jitter were never used in training.
